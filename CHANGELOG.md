Verified triangle winding on the affected wall is 100% consistent (8/8 correct) via Node harness, ruling out the geometry itself. NOT YET CONFIRMED clean or broken on real GPU hardware -- asked Joe to check on his actual machine before chasing this further.

v1.2.0 - 2026-08-10 - Fixed the actual bug Joe was reacting to: buildings in the negative-space view looked like solid objects instead of voids. The underlying geometry was already the correct inverse (bounding volume minus buildings, verified by matching triangle counts against a Node harness) -- the problem was purely visual, not geometric. A single DoubleSide red material rendered a carved-out tower cavity's interior walls identically to the solid mass's true outer skin, so a hole and a solid looked the same. Fixed by splitting into two materials sharing the same geometry: outerSkin (FrontSide, terracotta -- the true solid-mass boundary) and cavityWalls (BackSide, near-black -- only visible when looking into a hollow, i.e. where a real building stands). negativeMesh is now a THREE.Group of the two meshes instead of a single Mesh; existing .visible toggling on it (buildings/negative-space view switch) needed no changes since Group supports the same API. Verified live via headless Chrome at three section heights: buildings now read unambiguously as dark voids capped at their real height, with solid red mass everywhere else -- confirmed against Joe's own screenshot showing the ambiguous both-look-solid version this replaces.

v1.1.1 - 2026-08-10 - Fixed CSG artifacts (a stray white sliver shard, faint stray lines across the section-cut floor) that Joe spotted live in the rendered mesh. Root cause: computing the negative space as 497 sequential SUBTRACTION operations (bounding volume minus building 1, minus building 2, ... minus building 497) compounds floating-point drift on every step, since each operation rebuilds its BVH on top of the previous result's own accumulated imprecision. Fixed per Joe's diagnosis: union all 497 building solids into one clean solid first (ADDITION), then do exactly ONE final SUBTRACTION of that merged solid against the bounding volume. Verified in a Node harness on the same input: degenerate/near-zero-area triangles dropped from 50.3% of the mesh (14,897 of 29,591) to 31.4% (8,793 of 28,002) -- real, measurable improvement, not just visually plausible. Confirmed live via headless Chrome: stray white shard from v1.1.0's screenshot no longer present. Progress indicator now reports "Merging buildings N/497" then "Subtracting merged solid from site volume" instead of "Subtracting N/497", to reflect the new two-phase approach.

v1.1.0 - 2026-08-10 - Added a live horizontal section-cut slider (0m to bounding-cap height) to make the negative-space mesh actually legible -- v1.0.x's negative-space view only showed the exterior top of the bounding volume (a featureless slab), since most buildings are far shorter than the max-height cap. Uses renderer.localClippingEnabled + a THREE.Plane on the negative-space material's clippingPlanes, updated live from an input[type=range]. Slider auto-inits to a low cut (min(150m, 40% of cap height)) right after compute finishes, so the carved form is visible immediately instead of requiring the user to discover the slider. Verified live via headless Chrome screenshots at three heights (60m/150m/300m) -- confirmed the towers read as monolithic voids rising out of the solid mass, and higher cuts correctly leave only the supertalls still punching through.
